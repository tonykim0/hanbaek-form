# 리팩토링 계획 (2026-08-22)

## 이 문서가 정하는 것

콘솔이 실제로 멈춘 사고(2026-08-21 `/payouts` 300초 타임아웃)를 계기로 세운다.
**무엇을 고칠지가 아니라 무엇을 안 고칠지를 먼저 못 박는다** — 장애를 계기로 전면
재작성에 들어가면 회귀 범위를 아무도 모르게 된다.

### 하지 않는 것

- **UI·컴포넌트 전면 재작성을 하지 않는다.** 화면 규칙(CLAUDE.md)과 부품 정본
  (`components/ui.tsx`)은 이미 한 벌로 모여 있다. 느린 원인은 화면이 아니라 조회다.
- **노션 가져오기·동기화를 만들지 않는다.** 병행기의 규칙이 그대로다 — dual-write 금지.
- **상태 축(Stage) 분리를 이번에 하지 않는다.** 아래 5단계 참조.

### 원칙

1. **한 단계 = 한 배포.** 섞으면 무엇이 회귀를 만들었는지 알 수 없다.
2. **고치기 전에 잰다.** 「느린 것 같다」로 시작하지 않는다 — 운영 DB 로 실측하고,
   고친 뒤 같은 측정을 다시 해서 숫자를 커밋 메시지에 남긴다.
3. **규칙은 타입이나 한 곳의 함수로 못 박는다.** 문장으로만 두면 다음 사람이 어긴다.

## 확인된 사실 (2026-08-21~22 실측)

운영 DB · 시험 현장 5건 기준. **데이터가 많아서 느린 것이 아니다.**

| 측정 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `listProjects` 반복 호출 | 2번째부터 영구 대기 | 55~257ms |

원인은 **저장소가 자기 커넥션 풀보다 많은 쿼리를 한꺼번에 던지는 것**이었다.
목록 조립(`recordsOf`)이 병렬 6개 + 단가·정산 규칙 = 8개인데 풀이 5였다.

## 단계

### 0단계 — 조회 동시성 (완료, 배포됨)

`lib/data/db-slot.ts` 한 곳에서 동시 쿼리를 4개로 묶는다(잎 쿼리만 감싼다 — 슬롯을
쥔 채 슬롯을 기다리면 서로를 막는다). 풀은 12로 올려 여유를 둔다.

- [x] `recordsOf`·규칙 조회에 적용
- [x] `/payouts` 협력사 경로는 상세를 세 개씩 끊어 읽는다 (2단계에서 전용 조회로 흡수)

### 1단계 — 권한 DTO 분리 (완료, 배포됨 — 커밋 9ad7496)

**왜 먼저인가**: 성능이 아니라 안전 문제다. 지금은 한 객체를 만든 뒤 금액을 null 로
지우므로, 새 필드를 더할 때마다 협력사 브라우저로 새어나갈 자리가 생긴다. 실제로
2026-08-21 정산 탭에서 마진 열을 화면에서 빼는 일이 있었는데, 그때 데이터는 이미
브라우저에 실려 있었다 — 화면에서 가리는 것으로는 부족하다는 규칙이 바로 이것이다.

**실제로 새고 있었다** (2026-08-22 운영 DB 실측): 정산 규칙이 통째로 나갔다 —
이름이 「환경부 승인 300,000원 → 착공 800,000원 → 준공마감 1,200,000원」이고
`steps.basis.unit` 에 전액이 있다. `planAmount` 는 null 로 지웠는데 같은 금액이 이 칸으로
샜고, 기성 차수의 트리거·산정방식·회수 상태, 안전관리비, 준공마감일도 함께 나갔다.

- [x] 한백 전용 값을 `AdminOnlyDetail` 묶음으로 모으고 **옵셔널**로 뒀다 — 협력사 응답에는
      그 키가 아예 없고, 화면은 `detail.admin?.…` 로 읽는다(타입이 없을 수 있음을 강제)
- [x] 협력사가 보는 정산 값은 메모뿐이다 (`PartnerSettlementView`)
- [x] `npm run check:leak` — 협력사 시점(영업사·시공사 각각)으로 금지 키를 검사한다.
      9가지 시점 통과. 규칙을 문장에서 실행 가능한 검사로 옮겼다.

남은 것: 라인 단가의 `margin` 은 키가 남고 값만 null 이다(값 자체는 안 나가므로 누수는
아니다). 라인 구조가 화면 여러 곳에서 쓰여 키를 빼는 파급이 커서 두었다 — 3단계에서
읽기 모델을 가를 때 함께 정리한다.

### 2단계 — 화면별 읽기 모델 (완료, 배포됨)

지금 `listProjects`·`listSettlements`·`listPayouts` 가 거의 같은 `ProjectRecord` 를
만든 뒤 화면마다 필요한 값만 골라낸다. 현장이 노션에서 이관되면 이 비용이 그대로 커진다.

범위를 **실제로 무거운 곳부터**로 좁힌다 (여섯 개를 한꺼번에 만들지 않는다):

1. [x] `listPayoutOverview(viewer)` — 관리자 이중 전체조회(쿼리 16)와 협력사 N+1
   (5현장이면 53)을 한 번의 읽기(8)로 합쳤다. `WAVE=3` 임시 조치와 쓰이지 않게 된
   `payoutsOfSummaries` 를 걷어냈다. **한백도 협력사도 같은 길** — 같은 것을 두 모양으로
   조립하면 금액이 갈릴 자리가 생긴다.
2. [x] 현장 상세 — `generateMetadata` 와 본문이 각각 `getProject` 를 불러 한 요청에
   상세를 두 번 조립했다. `react cache` 로 요청 단위 한 번으로 묶었다(인자는 원시값이어야
   캐시가 듣는다 — viewer 객체를 넘기면 매번 새 키가 된다).
3. [ ] `listTodos(viewer)` — **하지 않았다.** 지금 `listProjects` 를 그대로 쓴다(63ms,
   쿼리 8). 필요한 컬럼만 읽는 전용 쿼리를 짜면 단계·반려·서류충족 같은 **유도 판정을
   다시 구현**해야 하고, 그 판정이 갈리는 것이 성능보다 큰 위험이다(보드와 할 일이 서로
   다른 답을 낸다). 3단계에서 읽기 모델을 제대로 가를 때 함께 한다.

**실측 (운영 DB)**

| | 전 | 후 |
|---|---|---|
| `/payouts` 관리자 | 120ms (쿼리 16) | **71ms (8)** |
| `/payouts` 협력사 | 271ms (8+9×N) | **66ms (8)** |
| 현장 상세 | 상세 2회 조립 | 1회 |

**회귀 확인**: 옛 경로와 새 경로가 같은 줄을 만드는지 협력사 9시점·관리자 전부 비교 —
불일치 0건, 금액 동일. `npm run check:leak` 통과.

### 3단계 — 저장소 3중 구현 정리 (완료, 배포됨)

**Codex 진단에 없던 항목이고, 앞으로의 작업 속도를 가장 크게 정한다.**

메서드 34개를 세 구현이 각자 적는다. 오늘 현장 멈춤·개명·삭제 기능을 넣을 때
인터페이스 1 + 구현 3 = 네 곳에 같은 판정을 적었다(`file-store` 주석에
「pg-store 와 같은 판정」이 반복 등장하는 것이 그 증거다). 판정이 두 벌이면 언젠가 갈린다.

**A 안으로 했다** — 개발 DB 를 분리하고(Supabase 프로젝트 하나 더) 파일 저장소를 걷어냈다.

- [x] 개발 DB 분리 — `.env.local` 이 개발용 프로젝트를 가리킨다. 로컬 `db:push`·`db:seed`
      가 프로덕션을 건드리지 않는다. 스키마는 이제 양쪽에 따로 반영해야 한다(CLAUDE.md 에 적음).
- [x] `lib/data/file-store.ts` (851줄) 삭제 — 로컬도 진짜 Postgres 를 본다.
- [x] `mockRepository` (메서드 34개가 전부 throw, 아무도 안 씀) 삭제. `mock.ts` 는 시드
      현장 5건만 남아 `db:seed` 가 쓴다(349줄 → 189줄).
- [x] `getRepository()` 는 `DATABASE_URL` 이 없으면 **멈춘다** — 빈 목록으로 조용히 도는
      것보다 낫다. 「데이터가 없다」와 「DB 를 못 본다」는 다른 일이다.
- [x] `repositoryKind()` 와 화면의 「예시 데이터입니다」 안내를 걷어냈다.

**결과**: 저장소 구현이 **세 벌 → 한 벌**(pg-store 35 메서드). 기능 하나에 네 곳을 고치던
것이 두 곳(인터페이스 + 구현)이 됐다. 데이터 계층 3855줄 → 2918줄(그 사이 2단계 기능이
늘었으므로 실제 중복 제거는 그보다 크다).

**남긴 것**: 파일(Vercel Blob)은 아직 로컬·프로덕션 공용이다 — 이관 전에 분리한다
(CLAUDE.md 「다음 할 일」 5번).

### 4단계 — 성능 회귀 감지 (완료, 배포됨)

이번 장애를 사용자 제보로 알았다는 것이 문제다.

- [x] `npm run perf` — 주요 조회를 3회씩 재고 임계(1초)를 넘으면 실패. 마지막에 네 조회를
      동시에 던져 고착을 본다. `npm run check` 로 누수 검사와 함께 돈다.
- [x] 느린 쿼리(700ms)·슬롯 대기(300ms) 경고 — 고착의 앞 신호를 로그에 남긴다.
      실제로 작동을 확인했다(네 조회 동시 → 「슬롯 대기 300ms」 로그).
- [x] 콘솔에 `loading.tsx`·`error.tsx` — **하나도 없었다.** 그래서 서버가 멈추면 본문이
      이전 화면에 머물고 탭의 로딩바만 돌았다(사용자가 겪은 그 증상). 이제 즉시 골격이
      뜨고, 터지면 다시 시도할 길과 오류 번호가 그 자리에 뜬다.

기준선(현장 5건): 목록·지급관리·기성·지급내역 각 50~160ms, 상세 96ms, 네 조회 동시 330ms.

### 5단계 — 상태 축 분리 (보류, 2~3일)

`lib/stage.ts` 의 `Stage` 는 배타적인데 계약·시공·정산은 실제로 동시에 존재한다
(기성 회수나 준공마감이 하나라도 있으면 전체를 `settlement` 로 분류한다).

세 축으로 가르는 것이 맞다: 계약 게이트 · 시공 진행 · 정산 진행.

**다만 지금 하지 않는다.** 보드 칸·게이트·탭 잠금·상세 첫 탭이 전부 이 축에 걸려 있어
회귀 범위가 크다. 잘못된 탭이 열리는 사례를 실제로 만나면 그때 한다 — 그 사례가
이 작업의 필요를 증명하고 테스트 케이스가 된다.

## 이관 전에 해야 하는 것 (2026-08-22 추가)

위 0~4단계는 「지금 아픈 것」이었다. 아래는 **노션 실현장을 콘솔 DB 로 옮기기 전에**
반드시 있어야 하는 것들이다 — 이관하는 순간 이 DB 의 현장이 실데이터가 되고, 없으면
그때부터 사고가 복구 불가능해진다. 실측으로 확인한 빈 자리다.

| 우선 | 항목 | 지금 상태 | 왜 이관 전인가 |
|---|---|---|---|
| **P0** | **백업·복구 절차** | **없음** | 실데이터가 되는 순간 사고 시 되돌릴 길이 없다. Supabase 무료 플랜은 PITR 이 없다 |
| **P0** | Blob 스토어 분리 | 로컬·프로덕션 공용 | 로컬에서 지우면 실계약서가 사라진다(Blob 은 휴지통이 없다) |
| **P0** | 스키마 반영 절차 | `db:push` 를 사람이 양쪽에 | 개발 DB 분리 뒤 프로덕션 반영을 잊으면 배포가 깨진다(오늘 실제로 겪었다) |
| **P1** | 감사 기록 조회 화면 | 쌓기만 하고 볼 화면이 없다 | 「누가 이 금액을 바꿨나」를 물을 때가 이관 뒤다 |
| **P1** | 이관 검증 도구 | 없음 | 옮긴 뒤 노션과 콘솔이 같은지 세어 보는 장치. 눈으로 138건을 대조할 수 없다 |
| **P2** | 노션 의존 제거 | `lib/notion.ts` 714줄 · 접수 라우트·서류 규칙이 참조 | 컷오버가 끝나야 걷어낼 수 있다 — 그때 자연히 사라진다 |

### P0 셋을 먼저 하는 이유

세 개 다 **「없으면 사고가 복구 불가」**에 걸린다. 나머지는 불편이지만 이것은 손실이다.

1. **백업** — `npm run db:dump` 로 현장·계정·정산을 파일로 떠내고, 되돌리는 스크립트도
   같이 만든다. 자동(cron)까지 갈지는 이관 규모를 보고 정한다. **떠낸 파일에 실계정 해시와
   계좌가 들어가므로 저장 위치를 먼저 정해야 한다** — 저장소에 넣지 않는다.
2. **Blob 분리** — 스토어를 하나 더 만들고 로컬 토큰만 교체(DB 와 같은 방식).
3. **스키마 반영** — `drizzle/` 마이그레이션 파일을 쓰거나(지금은 `db:push` 직접 적용이라
   이력이 없다), 최소한 「배포 전 프로덕션 DB 에 컬럼이 있는지」 확인을 `npm run check` 에 넣는다.

### 여기 넣지 않은 것

- **테스트 프레임워크·큰 파일 분해** — 화면과 규칙이 매주 바뀌는 동안은 테스트가 먼저
  낡고, 파일을 갈라도 곧 다시 뭉친다. 모양이 굳은 뒤에 한다. 지금은 `check:leak`·`perf`
  두 개가 회귀를 잡는 최소한이다.
- **상태 축 분리(5단계)** — 아래 보류 이유 그대로.

## 순서와 이유

```
0 동시성 → 1 권한 DTO → 2 읽기 모델 → 3 저장소 정리 → 4 회귀 감지   ← 여기까지 완료·배포
  장애 해소   안전        성능·이관 대비   작업 속도       재발 방지
                                    ↓
                    P0: 백업 · Blob 분리 · 스키마 반영 절차   ← 이관 전 필수
                                    ↓
                              이관 · 컷오버
                                    ↓
              노션 제거 · 테스트 · 큰 파일 분해 · [상태 축]   ← 모양이 굳은 뒤
```

- 1단계가 2단계보다 먼저인 이유: 읽기 모델을 새로 만들면서 권한 경계를 그으면 두 번 안 짠다.
- 3단계가 2단계 뒤인 이유: 읽기 모델이 정해지기 전에 구현을 합치면 합친 것을 또 고친다.
- 4단계를 마지막이 아니라 3단계 뒤에 두는 이유: 그때부터 코드가 자주 바뀐다.
