# 리팩토링 계획 2 — 전체 리뷰 (2026-08-22)

첫 계획서(`REFACTOR_PLAN.md`)는 장애에서 출발해 조회 계층을 고쳤고 0~4단계가 끝났다.
이번은 **장애와 무관하게 프로젝트 전체를 훑어** 나온 것이다. 실측 근거를 같이 적는다.

## 먼저 — 건강한 부분 (고치지 않는다)

훑어보니 이미 잘 잡혀 있는 것이 있다. 리팩토링 대상으로 착각하지 않게 적어 둔다.

| 지표 | 값 | 뜻 |
|---|---|---|
| `as any` | **1건** | 타입 탈출구가 거의 없다 |
| `@ts-ignore` · `: any` | **0건** | 컴파일러를 끄고 넘어간 자리가 없다 |
| `TODO`·`FIXME`·`HACK` | **0건** | 미룬 것을 주석으로 남기지 않았다 |
| 빈 `catch {}` | **0건** | 조용히 삼키는 자리가 없다 |
| 부품 정본 | `components/ui.tsx` + `/design` | 모양이 한 곳에 모여 있다 |
| 판정 정본 | `lib/stage.ts`·`lib/process.ts`·`lib/doc-rules.ts` | 화면이 다시 세지 않는다 |

**그래서 이 계획은 「코드를 예쁘게」가 아니라 「같은 것을 여러 곳에 적는 구조」와
「보호가 없는 자리」만 다룬다.**

## A. 운영사(CPO)를 하나 더 붙일 때 다섯 곳을 고친다 — 가장 큰 중복

실측: 운영사별로 같은 모양이 네다섯 벌 있다.

| 무엇 | 파일 | 줄 |
|---|---|---|
| 양식 채우기 | `fillDocx.ts` · `fillDocx-hec` · `-nice` · `-sk` | 317 + 499 + 415 + 389 = **1620** |
| 폼 스키마 | `schema.ts` · `schema-hec` · `-nice` · `-sk` | 4벌 |
| 포털 화면 | `(portal)/hec` · `nice` · `sk` · `pluglink` | 257+204+180+175 = **816** |

에버온을 붙이려면 이 다섯 자리를 복제해야 하고, 규칙이 하나 바뀌면 네 곳을 같이 고쳐야
한다. 실제로 오늘 재발행 수정(회전 판독)은 한 곳이라 다행이었지만, 양식 규칙이 바뀌면
그렇지 않다.

**방향**: 운영사마다 다른 것(필드 좌표·문구·조건)을 **자료로 빼고** 채우는 코드는 한 벌로
둔다. 지금 네 파일의 차이를 먼저 표로 뽑아 「진짜 다른 것」이 얼마인지 재는 것이 1일차 일이다
— 차이가 크면 공용화가 오히려 조건문 지옥이 되므로, 재보고 결정한다.

- 범위: 2~4일. **운영사를 추가할 일이 생길 때 착수한다** — 그때가 이 비용을 실제로 치르는 시점이고,
  새 운영사가 요구사항의 표본이 된다. 지금 미리 하면 표본 없이 추상화한다.

## B. 무로그인 API 에 남용 방지가 없다 — 비용·가용성

포털은 로그인이 없으므로 이 라우트들은 **의도적으로** 열려 있다. 문제는 보호가 없다는 것이다.

| 라우트 | 하는 일 | 열려 있어서 생기는 것 |
|---|---|---|
| `/api/import-form` | PDF 를 **Opus** 로 판독 (`maxDuration=300`) | 요청마다 API 비용. 반복 호출로 비용·함수 슬롯 소모 |
| `/api/upload` | Blob 업로드 토큰 발급 (최대 100MB) | 저장소를 채울 수 있다 |
| `/api/intake` | 접수 → 노션 기록 | 쓰레기 접수가 노션에 쌓인다 |
| `/api/kapt/*` | 공개 조회 | 상대적으로 무해 |

★`/api/import-form` 이 가장 급하다★ — 화면(`/admin/reissue`)은 로그인 뒤인데 API 는
누구나 부를 수 있고, 한 번 부를 때마다 Opus 판독이 돈다.

**방향**: IP·세션 단위 호출 제한(간단한 메모리 토큰버킷으로 시작), 파일 크기·페이지 상한
재확인, 포털 폼에 최소한의 사람 확인. 서버리스는 인스턴스가 여럿이라 메모리 제한이 완벽하진
않지만, 지금은 **없는 것과 있는 것의 차이**가 크다.

- 범위: 1일. **바로 한다** (아래 순서 참조).

## C. 죽은 코드 — 18개+ 미사용 export, 미사용 패키지 3개

실측: 다른 파일에서 한 번도 쓰이지 않는 export 18개 이상
(`lib/notion.ts` 5개, `lib/doc-category-map.ts` 2개, `lib/process.ts` 의 `contractNeedsFix` 등),

읽는 사람이 「이건 어디서 쓰나」를 매번 확인해야 하고, 지울 때 무섭다.

**방향**: 한 번에 지우지 않는다. `lib/notion.ts` 는 이관 때 통째로 사라질 파일이므로 건드리지
않고, 그 밖의 것만 걷는다. 패키지는 확인 후 제거(`zod` 는 앞으로 검증에 쓸 계획이 있으면 남긴다).

- 범위: 반나절. **A·B 사이 틈에 한다.**

## D. 큰 화면 파일 — 지금은 아니다

`IntakeForm.tsx` 1050줄, `PricingMatrix.tsx` 1010, `ConstructionTab.tsx` 758,
`ProjectTable.tsx` 704, `pg-store.ts` 1791.

**줄 수는 병이 아니다.** 이 파일들은 각자 한 가지 일을 하고 있고, 오늘 여러 번 고쳤지만
「어디를 고쳐야 하는지 못 찾는」 일은 없었다. 갈라야 할 신호는 두 가지다 —
① 한 파일을 두 사람이 동시에 고쳐 충돌이 반복될 때 ② 한 화면의 한 부분만 고치려는데
관계없는 코드가 계속 딸려올 때. **그 신호가 오면 그 파일만 가른다.**

## E. 요청마다 다시 읽는 것 — 관찰만

`/api/todos` 는 메뉴를 옮길 때마다 현장 전체를 조립한다(현장 5건에 63ms).
첫 계획서 2단계에서 경량화를 **의도적으로 하지 않았다** — 유도 판정(단계·반려·서류충족)을
다시 구현하면 보드와 할 일이 다른 답을 낼 수 있고, 그것이 63ms 보다 큰 위험이다.

**이관 후 현장이 100건을 넘으면 다시 본다.** 그때는 `npm run perf` 가 먼저 알려줄 것이다.

## 순서

```
B 남용 방지 (1일)  →  C 죽은 코드 (반나절)  →  [이관 전 P0: 백업·Blob·스키마]
     지금 급함            정리                    첫 계획서 참조
                              ↓
                     A 운영사 공용화 — 운영사를 추가할 때
                     D 파일 분해 — 충돌·간섭이 생길 때
                     E todos 경량화 — 현장 100건 넘을 때
```

**B 를 먼저 하는 이유**: 다른 것은 「나중에 아플 것」이지만 이것은 **지금 열려 있다**.
비용이 새는 자리이고, 고치는 데 하루면 된다.

**A·D·E 를 조건부로 둔 이유**: 세 개 다 「미리 하면 표본 없이 추상화」가 된다. 계기가
곧 요구사항이고 테스트다. 이 문서에 조건을 적어 두었으므로 그때 알아볼 수 있다.

## 상태 갱신

- **B 무로그인 API 남용 방지 — 아직 미착수. 여전히 1순위다.** `/api/import-form` 은
  `maxDuration=300` 에 Opus 판독이 무제한으로 열려 있다. 첫 리뷰에서 「지금 급함, 1일」
  이라 적었고 이틀이 지났다.
- **첫 계획 P0 — 남은 것은 백업·Blob 분리 둘이고, 긴급도가 바뀌었다.** 이관 스크립트가
  완성돼 실행이 임박했고, 세금계산서(실서류)가 이미 Blob 에 들어가기 시작했다.
  「이관 전 필수」가 「이번 주」가 됐다. --wipe 가 tax_invoices·batch_finals 까지 지우는
  것도 백업이 먼저 있어야 안전하다.
- **C 죽은 코드 — 갱신.** zod 미사용 확정(제거 가능). `scripts/` 20개 중 7개가 일회성
  (print-*·apply-*) — 정책 SQL 을 뽑고 나면 수명이 끝난 것들이다. migrations/ 에 결과가
  남았으므로 지워도 된다. 반나절.
- **D 큰 파일 — 신호가 오는 중이다.** PricingMatrix.tsx 1,765줄(+755), 이번 주 커밋 12회.
  pg-store.ts 2,113줄(+322), 8회. 여러 세션이 같은 파일을 며칠째 만지고 있다 — ①번 신호
  (동시 수정)가 근접했다. 다음에 이 둘에서 병합 충돌이나 「남의 미완성 작업에 밟히는」 일이
  생기면 그때 가른다: PricingMatrix 는 폼/격자/목록 셋으로, pg-store 는 배치·세금계산서
  묶음(이미 응집돼 있다)부터.
- **E todos — 더 무거워졌다(관찰 유지).** 협력사 발행 알림이 붙어 화면 이동마다
  listProjects + listPayouts + listBatchFinals 셋을 병렬로 돈다. 지금은 통과. **이관으로
  현장이 실규모(수백 건)가 되면 perf 가 먼저 알릴 것** — 그때 본다.
