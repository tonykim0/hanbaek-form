## 먼저 — 건강한 부분 (고치지 않는다)

훑어보니 이미 잘 잡혀 있는 것이 있다. 리팩토링 대상으로 착각하지 않게 적어 둔다.

| 지표 | 값 | 뜻 |
|---|---|---|
| `as any` | **1건** | 타입 탈출구가 거의 없다 |
| `@ts-ignore` · `: any` | **0건** | 컴파일러를 끄고 넘어간 자리가 없다 |
| `TODO`·`FIXME`·`HACK` | **0건** | 미룬 것을 주석으로 남기지 않았다 |
| 빈 `catch {}` | **0건** | 조용히 삼키는 자리가 없다 |
| 부품 정본 | `components/ui.tsx` + `/design` | 모양이 한 곳에 모여 있다 |
| 판정 정본 | `lib/stage.ts`·`lib/process.ts`·`lib/doc-rules.ts` | 화면이 다시 세지 않는다 |

**그래서 이 계획은 「코드를 예쁘게」가 아니라 「같은 것을 여러 곳에 적는 구조」와
「보호가 없는 자리」만 다룬다.**

## A. 운영사(CPO)를 하나 더 붙일 때 다섯 곳을 고친다 — 가장 큰 중복

실측: 운영사별로 같은 모양이 네다섯 벌 있다.

| 무엇 | 파일 | 줄 |
|---|---|---|
| 양식 채우기 | `fillDocx.ts` · `fillDocx-hec` · `-nice` · `-sk` | 317 + 499 + 415 + 389 = **1620** |
| 폼 스키마 | `schema.ts` · `schema-hec` · `-nice` · `-sk` | 4벌 |
| 포털 화면 | `(portal)/hec` · `nice` · `sk` · `pluglink` | 257+204+180+175 = **816** |

에버온을 붙이려면 이 다섯 자리를 복제해야 하고, 규칙이 하나 바뀌면 네 곳을 같이 고쳐야
한다. 실제로 오늘 재발행 수정(회전 판독)은 한 곳이라 다행이었지만, 양식 규칙이 바뀌면
그렇지 않다.

**방향**: 운영사마다 다른 것(필드 좌표·문구·조건)을 **자료로 빼고** 채우는 코드는 한 벌로
둔다. 지금 네 파일의 차이를 먼저 표로 뽑아 「진짜 다른 것」이 얼마인지 재는 것이 1일차 일이다
— 차이가 크면 공용화가 오히려 조건문 지옥이 되므로, 재보고 결정한다.

- 범위: 2~4일. **운영사를 추가할 일이 생길 때 착수한다** — 그때가 이 비용을 실제로 치르는 시점이고,
  새 운영사가 요구사항의 표본이 된다. 지금 미리 하면 표본 없이 추상화한다.

# 재리뷰 3 (2026-08-27) — API 토큰 관점, 그리고 재사용성

두 가지 요청이었다: ①API 토큰을 효율적으로 쓰는 계획 ②다른 관점(재사용성 등)의 계획.
전자는 **실측부터** 했다 — 어림으로 정하면 엉뚱한 것을 먼저 고치게 된다.

## 실측 (count_tokens, claude-opus-5)

| 무엇 | 토큰 | 요청당 비용(입력 $5/M) |
|---|---|---|
| 판독 지시문 (`buildFormImportPrompt`) | **5,296** | $0.026 |
| 스캔 계약서 11쪽 (실파일 5.2MB) | **19,621** (쪽당 ~1,784) | $0.098 |
| 60쪽 상한(`MAX_PAGES`)까지 갔을 때 | **≈107,000** | ≈$0.53 |

**결론: 돈은 문서가 쓴다.** 지시문은 전체의 5~20% 다. 그래서 「프롬프트를 다듬자」가 아니라
**「보내는 페이지를 줄이고, 같은 문서를 두 번 보내지 말자」**가 1순위다.

호출 자리는 셋이고 전부 `claude-opus-5` 다: `lib/claude-import.ts`(계약서, effort high,
max_tokens 16000, 재시도 2), `lib/claude-partner-doc.ts`(사업자등록증·통장, 재시도 2),
`lib/intake-review.ts`(접수 검토, max_tokens 4096).

## T0. 무로그인 판독 API 에 상한이 없다 — ~~여전히 B 항목~~ **닫았다 (2026-08-27)**

**해결**: `/api/import-form` 과 그 앞의 업로드 토큰(`/api/upload`)에 세션을 요구한다.

400 이 아니라 401 이 와야 한다.

★대가★: 포털에서 로그인 없이 쓰던 「스캔본으로 폼 되돌리기」가 닫힌다. 콘솔로 들어와
쓰면 그대로 된다(콘솔 주소에서 포털 양식이 열린다). 포털 접수를 닫은 것과 같은 방향이다.

아래는 닫기 전의 기록이다.

`/api/import-form` 이 열려 있고, 부를 때마다 Opus 판독이 돈다. 위 실측으로 말하면

(첫 리뷰의 B, 나흘째 밀림).

## T1. 보내는 페이지를 결정적으로 고른다 — 가장 큰 절감

`limitPages` 는 앞 60쪽을 자를 뿐 **무엇을 자를지 모른다**. 판독에 필요한 것은 계약서·
별지5호·별지7호·직인동의서 몇 쪽인데, 협력사가 스무 장씩 묶어 보내면 전부 판독한다.

**방향**: PDF 에서 텍스트를 뽑아(`pdf-lib` 로는 안 되니 이미 쓰는 도구로) 표지 문자열
(「별지 제5호」·「별지 제7호」·「직인 사용 동의서」·「설치 신청서」)이 있는 쪽만 보낸다.
텍스트가 없는 순수 스캔본은 지금처럼 전량 — 그때만 비싸다. 절감폭은 그 현장 서류 구성에
달렸지만, 20쪽 → 8쪽이면 요청당 20K 토큰이 준다. 반나절.
★결정적 전처리가 AI 판독보다 먼저다★ — 같은 원칙을 회전 보정(`uprightPdf`)에서 이미 썼다.

## T2. 같은 문서를 두 번 보내지 않는다 — Files API + 캐시

지금은 base64 로 매 요청 싣는다. 그래서 **재시도 한 번이 문서 값을 두 배로 만든다**
(`MAX_ATTEMPTS = 2`). 접수 자동판독과 검토가 같은 파일을 보는 경로도 각자 올린다.

**방향**: `client.beta.files.upload` (베타 `files-api-2025-04-14`)로 한 번 올리고
`{type:'document', source:{type:'file', file_id}}` 로 참조한다. 재시도·재판독이 업로드
없이 돈다. 덧붙여 문서 블록에 `cache_control` 을 걸면 재시도가 캐시 읽기(입력의 ~10%)가 된다.

## T3. 재시도를 문서 없이 한다

첫 시도가 JSON 파싱/스키마로 죽으면 60쪽을 다시 보낸다. 파싱 실패는 structured outputs 로
이미 드물어졌으니, 재시도를 갈라야 한다:
· 5xx·타임아웃 → 문서와 함께 재시도(지금 동작)
· 파싱·스키마 위반 → **문서 없이** 「방금 응답을 이 스키마에 맞춰 다시 내라」 (입력 수백 토큰)

## T4. 지시문을 system 으로 올리고 캐싱한다

`cache_control` 이 코드에 한 번도 없다(grep 0). 게다가 content 순서가 **[문서][지시문]** 이라
정적 지시문이 매 요청 바뀌는 문서 뒤에 온다 — 접두사 캐시가 성립할 수 없는 순서다.

**방향**: 지시문(정적, 5,296토큰)을 `system` 에 `cache_control:{type:'ephemeral'}` 로 두고,
파일명·페이지수·CPO 힌트처럼 **요청마다 바뀌는 것은 messages 의 text 블록으로 내린다**
(그것이 지금 지시문 안에 박혀 있어 캐시를 깬다). 캐시 읽기는 입력의 ~10% — 요청당
약 4.8K 토큰이 준다. 최소 캐시 길이 1024토큰은 넉넉히 넘는다. 반나절.

## T5. 경로마다 effort 를 따로 준다

계약서 판독은 `effort: high` 가 맞다. 그런데 사업자등록증에서 상호·주소·대표자를 뽑는 일과
접수 검토는 그만한 추론이 필요 없다 — 그 둘을 `low`/`medium` 으로 내린다.
★모델은 내리지 않는다★ — 비용을 이유로 Opus 를 Sonnet 으로 바꾸는 것은 우리가 정할 일이
아니고(품질 저하가 조용히 온다), effort 가 같은 일을 더 정직하게 한다.

## 다른 관점 — 재사용성·구조 (이번 세션에서 실제로 밟은 것들)

### I. 화면의 「진행 조건」과 서버의 게이트가 두 벌이다 — **한 벌로 (2026-08-27)**

**해결**: 게이트가 `met: boolean` 이 아니라 **없는 것의 목록**(`Blocker[]`)을 돌려준다.
화면(`AdvanceRow`)은 판정하지 않고 `advanceBlockers(target, 선언칸, p)` 의 첫 항목을 단추
이름에 적는다. 선언을 하기 위한 조건(`CHECK_REQUIRES`)도 게이트 옆에 뒀다 — 「선언이
있는가」(게이트)와 「선언을 할 수 있는가」(화면)가 서로 다른 물음이라 둘 다 필요한데,
나뉘어 있으면 또 어긋난다. `need` 문자열도 없앴다(그것도 손으로 맞추던 두 번째 벌이었다).

시험에서 실제로 버그를 하나 잡았다: 수량 조건을 `=== null` 로 적어 값이 `undefined` 면
「있다」로 셌다. `== null` 로 고쳤다.

아래는 고치기 전의 기록이다.

`ConstructionTab` 의 `advance.ready`(무엇이 차면 단추가 열리나)와 `lib/process.ts`
`STATUS_GATES[...].met`(무엇이 차면 넘어가나)이 **같은 규칙을 두 번 적는다**. 2026-08-26
충전기 발주 조건을 넣을 때 두 목록을 손으로 맞췄고, 모뎀 발주 수량을 한쪽에 빠뜨렸다가
고쳤다. 어긋나면 「단추는 활성인데 서버가 거절」이 되고 이유를 알 수 없다.

**방향**: 게이트가 `met: boolean` 이 아니라 **「무엇이 없나」의 목록**을 반환하게 하고,
화면은 그 첫 항목을 단추 이름에 적는다. 그러면 판정이 한 벌이다. 반나절.

### J. 상자를 문자열 이름으로 분기한다 — ~~이미 사고가 났다~~ **고쳤다 (2026-08-27)**

**해결**: 그룹 spec 에 `extras: GroupExtra[]` 를 두고, `extraRow` 의 switch 가 그린다.
이름은 라벨로만 남는다. 목록에 종류를 더하고 case 를 안 적으면 `const missing: never = x`
에서 컴파일이 깨진다 — 실제로 시험했다(가짜 종류를 넣으니
`Type '"testOnly"' is not assignable to type 'never'`). 조용히 안 그려지는 길이 막혔다.

아래는 고치기 전의 기록이다.

`g.title === '충전기'` 로 모델·수량 줄을 그렸는데, 2026-08-26 상자 이름을 「충전기 발주」로
바꾸자 **그 세 줄이 통째로 화면에서 사라졌다**(타입 검사도 통과했다 — 문자열이니까).

**방향**: 그룹 spec 에 무엇을 그릴지 적는다(`extras: ['chargerModel', 'orderQty']`).
이름은 표시용이 되고, 이름을 바꿔도 내용이 사라지지 않는다. 2시간.

### K. 서류 하나 추가에 세 곳을 고친다 — **두 곳으로 (2026-08-27)**

**해결**: 종류·이름·조건이 `lib/doc-rules.ts` 한 곳에 있다. 조건부 서류는 정의 옆에
`only: (c) => …` 로 적고(전기안전관리자 선임신고증명서 = 한전불입만), `processDocsFor(keys, ctx)`
가 걸러 준다 — 화면이 판정하지 않으므로 서버도 같은 함수로 「이 현장에 이 서류가 필요한가」를
물을 수 있다. 상자에는 **배치만** 남는다(어느 상자에 뜨나).

배치 목록에 타입을 줬다(`ProcessDocKey[]`). 예전에는 `string[]` 이라 오타가 조용히 지나갔다
— 못 찾으면 아무것도 안 그리고 끝났다(J 와 같은 갈래). 시험했다: 키를 `useInspct` 로
바꾸니 컴파일이 깨진다. 조건 필터도 확인했다 — 한전불입·혼용 6칸, 모자분리·미지정 5칸.

남은 한 곳은 **필수 여부**(게이트)다. 지금은 `STATUS_GATES` 가 서류 키를 직접 본다
(`docApproved(p, 'completeConfirm')`) — 서류 정의로 옮길 수 있지만, 「어느 칸을 여는가」는
단계의 일이라 지금 자리가 더 맞다고 봤다. 조건: 서류가 스무 개를 넘거나, 같은 서류가 두
단계에서 필수가 되면 그때 옮긴다.

아래는 고치기 전의 기록이다.

종류(`PROCESS_DOCS`) · 어느 상자에 뜨나(그룹의 `docs` 배열) · 필수인가(`STATUS_GATES`).
2026-08-27 준공 서류 여섯 개를 넣으며 세 곳을 손으로 맞췄다. 조건부 서류(전기안전관리자
선임신고증명서 = 한전불입만)는 화면 쪽에만 조건이 있어, 서버는 그 현장에 그 서류가
필요한지 모른다.

**방향**: 서류 정의 한 곳에 `stage`·`required(ctx)` 를 함께 적는다 — 계약 서류가 이미
그 꼴이다(`lib/doc-rules.ts` 의 `req: (c) => 'm'|'o'`). 공정 서류만 그 규칙 밖에 있다. 반나절.

### L. 단계 이름이 DB 에 글자로 담긴다 — 관찰만

`processes.status` 가 표시 이름 그대로다. 그래서 이름을 바꿀 때마다 마이그레이션이 붙는다
(2026-08-27 `0031`, 「시공진행필요 → 충전기 발주」). 코드값과 표시 이름을 가르면 없앨 수
있지만, 지금 DB·보드·표·게이트가 다 그 글자를 쓰고 있어 수술이 크다.
**조건**: 이름을 또 바꿔야 할 일이 생기면 그때 가른다. 지금은 적어만 둔다.
