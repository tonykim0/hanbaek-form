## 0. 한 줄 원칙

**하나의 현장(project)이 접수 → 시공 → 정산 단계를 통과하며, 데이터가 앞에서 뒤로 흐른다.**
세 기능이 아니라, 한 데이터 모델 위의 세 화면이다.

특히: **입력이 돈으로 이어진다.** 시공에서 마일스톤을 입력하면 정산에서 기성 청구가 자동으로 열린다.
이 연결이 이 시스템의 존재 이유다. 접수/시공/정산을 따로 만들면 이 연결이 안 생기므로, 처음부터 통합 모델로 짠다.

## 0-1. ★데이터 전략 — 노션 병행, 추상화 계층★ (구현의 대전제)

**현재 상태 (실제)**: hanbaek-form이 접수를 받아 Anthropic API로 자동분류하고, 결과를 **노션에 저장**한다.
즉 지금 노션이 백엔드로 살아서 돌고 있다. Claude Console로 API 연동이 이미 되어 있음.

**방침**: **웹앱이 완전해질 때까지 노션을 병행 유지한다.** 지금 돌아가는 걸 부수지 않는다.
따라서 노션을 당장 Postgres로 갈아엎지 않는다. 대신:

```
[접수/시공/정산 화면]
        │
        ▼
[데이터 접근 추상화 계층]  ← getProject(), saveDocument(), updateSettlement() 등 인터페이스
        │
        ▼
[구현: 지금은 노션 API]  →  (웹앱 완성 후) [구현: 자체 Postgres]로 교체
```

- 화면·비즈니스 로직은 추상화 인터페이스만 호출. 그 뒤가 노션인지 DB인지 모르게.
- 처음 세운 데이터 모델(§6)은 **버리지 않는다** — 그게 추상화 계층의 인터페이스 스키마가 된다.
  구현만 노션 API로 채운다. 나중에 같은 인터페이스를 Postgres 구현으로 바꿔 끼운다.
- **절대 dual-write 금지**: 한 필드를 노션과 다른 곳에 동시에 쓰지 않는다. 각 데이터의 정본은 한 곳.
  지금은 노션이 정본. 모듈별로 정본을 옮길 때 한 번에 옮기고, 겹쳐 쓰지 않는다.

**Claude Code Phase 0의 최우선 작업**: 지금 API route 코드를 읽어라.
1. 접수 시 노션의 어느 DB/속성에 무엇을 쓰는지 (계약 마스터? 어느 필드?)
2. 자동분류가 정확히 뭘 하는지 — 파일 종류를 판별해 노션 첨부 슬롯에 꽂나?
   노션 현장 페이지의 `01_` `02_` 번호 붙은 파일이 이 자동분류 결과물인가?
3. Anthropic API 호출 방식(어떤 프롬프트로 분류하는지), 노션 API 래퍼가 어디 있는지
→ 이걸 파악해야 추상화 계층의 노션 구현을 어떻게 짤지 정해진다.

## 1. 노션의 3-DB 구조 = 그대로 우리 도메인 모델

노션이 이미 이 구조로 되어 있고(정산 DB 스키마에서 확인됨), 우리도 같은 관계를 쓴다.

```
project (현장)  ──1:N──  contract_line (계약 라인)   ← 한 현장에 7년3대+10년4대 등 복수
   │                          │
   │                          └── pricing_rule (적용 단가 규칙, 한백이 지정)
   │
   ├──1:1──  process (공정)     ← 마일스톤 날짜들 + 서류 슬롯
   │
   └──1:1──  settlement (정산)  ← 기성 1/2/3차, 지급정책, 회수 상태
                  │
                  └── payment_policy (운영사 지급정책)  ← 1/2/3차 트리거·유형·대당금액
```

## 3. ★공정 → 정산 트리거★ (이 시스템의 심장) — 실제 데이터로 확정됨

**중요 발견**: 지급정책은 별도 DB가 아니라 **단가 매트릭스(dec6088d…)의 컬럼**이다.
매트릭스 케이스 한 행에 단가(영업비/시공비/마진)와 기성 트리거(1/2/3차)가 함께 있다.
즉 접수에서 "적용 단가 규칙"을 지정하면 → 단가와 기성 트리거가 **동시에** 확정된다.
(정산 DB의 `운영사 지급정책` relation은 이 매트릭스를 가리키는 것. 별도 정책 테이블 만들 필요 없음)

### 트리거 종류 (전 케이스 실측 — 딱 4가지)
`환경부 승인` · `착공` · `준공마감` · `해당없음`

각 케이스는 (1차/2차/3차) × (트리거, 유형, 대당금액)을 가진다.
- 유형: `정액`(대당금액 그대로) 또는 `잔액`((턴키단가 - 앞단계정액합) × 대수) 또는 `해당없음`
- 대부분 2단계(1차+2차), 현대엔지니어링만 3단계, 자체투자·시공만은 1단계.

### 운영사별 트리거 패턴 (실측)
```
플러그링크   : 1차=환경부 승인(정액 20만) → 2차=준공마감(잔액)           [2단계]
나이스인프라 : 1차=착공(정액 110만)        → 2차=준공마감(잔액)           [2단계]
SK일렉링크   : 1차=착공(정액 80만)         → 2차=준공마감(잔액)           [2단계]
현대엔지니어링: 1차=환경부 승인(정액) → 2차=착공(정액) → 3차=준공마감(정액) [3단계]
에버온       : 1차=환경부 승인(정액) → 2차=준공마감(정액)                [2단계]
자체투자(SK) : 1차=준공마감(정액, 일시금)                               [1단계]
시공만       : 1차=준공마감(정액, 시공비만)                             [1단계]
```
※ 같은 운영사도 상/하반기·수전방식·계약기간·신규/교체·사업구분에 따라 케이스가 갈림.
   케이스 선택 축 = 운영사 + 사업구분 + 수전방식 + 계약기간 + 신설·교체 + (상/하반기 적용시작일).

### 트리거 → 공정 이벤트 매핑 (구현 규칙)
```
트리거 "환경부 승인"  ← process.환경부_승인일 이 채워지면 열림
트리거 "착공"        ← process.실착공일 이 채워지면 열림
트리거 "준공마감"     ← process.준공서류일(또는 준공 상태=완료) 이면 열림
트리거 "해당없음"     ← 그 차수는 없음 (표시 안 함)
```
**정산 자동화 로직**:
```
각 정산행에 대해, 적용 케이스의 N차_트리거를 읽는다.
그 트리거에 대응하는 공정 이벤트가 완료됐으면 → 기성 N차를 "청구 가능"으로 표시 + 알림.
회수 체크(기성_N차_회수=YES)되면 회수액/회수율 갱신.
```

### 기성 금액 공식 (실측)
```
1차_금액 = (1차_유형=정액) ? 1차_대당금액 × 계약대수 : 잔액계산
2차_금액 = (2차_유형=정액) ? 2차_대당금액 × 계약대수
                          : (턴키단가 - 앞단계정액합) × 계약대수   // 잔액
턴키단가(대당) = 영업비 + 시공비 + 한백마진   // 매트릭스 케이스에 있음
기성_계획총액 = 1+2+3차 금액 합
회수율 = 회수액 ÷ 계획총액 × 100
```

### 단가 매트릭스 실제 컬럼 (dec6088d…)
케이스명, 운영사명(표준), 사업구분, 수전방식, 계약기간, 건축물유형, 신설·교체, 사업연도, 적용시작일,
영업비, 시공비, 한백마진, 운영사턴키단가(formula), 협력사배포단가(formula),
1/2/3차_트리거, 1/2/3차_유형, 1/2/3차_대당금액,
감리비용 부담(영업비 차감 등), 전기안전점검수수료 부담(한백 부담 등), 비고(프로모션 등).
→ **INTAKE_SPEC의 예시 단가(RULES)는 이 실제 매트릭스로 교체.** 미결질문 2번 해소됨.

## 3-1. ★관리자 — 단가 매트릭스 관리★ (한백 전용)

단가 매트릭스는 하드코딩하지 않는다. **한백이 관리자 화면에서 직접 케이스를 관리**한다.
반기마다 단가가 바뀌고(상/하반기), 프로모션·신규 운영사가 생기므로 한백이 코드/노션을 건드리지 않고 관리해야 함.

### 기능
- **케이스 목록**: 운영사·조건별 필터, 적용시작일 기준 현행/만료 구분.
- **케이스 추가/수정/복제**: 한 케이스 = {운영사, 사업구분, 수전방식, 계약기간, 신설·교체, 건축물유형,
  적용시작일, 영업비, 시공비, 한백마진, 1/2/3차 (트리거·유형·대당금액), 감리비 부담, 전안수수료 부담, 비고}.
  기존 케이스 복제해서 반기 단가 새로 만드는 흐름이 잦을 것(상반기→하반기).
- **비활성화**(soft delete): 지난 케이스는 지우지 말고 비활성. 과거 현장이 참조 중일 수 있음.
- **버전/이력**: 케이스 수정 시 이력 남김. 단, **금액 소급은 없음** — 이미 그 케이스로 지정된 현장은
  지정 시점 값을 계약 라인에 스냅샷으로 갖고 있어(아래 확정 불변식) 매트릭스 수정과 무관.
  즉 매트릭스 수정은 "앞으로 지정할 계약"에만 영향.

### ★확정된 불변식 — 단가 지정은 스냅샷★ (한백 실무 확인 완료)
접수에서 계약 라인에 매트릭스 케이스를 지정하면, **그 시점의 단가·트리거를 계약 라인에 복사(스냅샷)**한다.
나중에 관리자가 매트릭스를 수정해도 **이미 지정된 현장의 금액·트리거는 안 바뀐다.**
→ `contract_lines`에 pricing_rule_id뿐 아니라 지정 당시 값(sales_unit, cons_unit, t1_trigger…)을 저장.
**단가는 계약 시점에 고정, 이후 매트릭스 변경 무관. 소급 적용 없음** — 한백 실무 관행으로 확정됨.
이유: 매트릭스는 미래 계약용 기준표. 과거 계약은 계약 당시 조건으로 고정돼야 함(정산 분쟁 방지).

### 검증 (트리거 정합성)
매트릭스가 기성 트리거를 담으므로, 관리자 입력 시 검증 필수:
- 트리거는 {환경부 승인, 착공, 준공마감, 해당없음} 중 하나만.
- 유형은 {정액, 잔액, 해당없음}. **잔액 유형은 마지막 활성 단계에만** 올 수 있음(그 앞은 정액).
- 1차는 항상 존재, 유형 ≠ 해당없음. 뒤 단계가 해당없음이면 그 뒤도 전부 해당없음.
- 잔액 계산엔 턴키단가(=영업비+시공비+마진) 필요 → 세 값 다 있어야 저장 가능.
- 저장 전 미리보기: "계약 N대 기준 1차 ○○원, 2차 ○○원(잔액), 합계 ○○" 계산해서 보여주기.

### 권한
- **한백 관리자만** 접근. 협력사는 매트릭스 자체를 못 봄(자기 현장에 지정된 결과 금액만 봄).
- 노션 병행기에는 매트릭스도 노션(dec6088d…)에 read/write. 추상화 계층 통해 접근.

## 4. 대시보드 (전체 조망)

단계 화면 위에, 60개 현장을 한눈에 보는 대시보드. 채팅에서 여러 안을 시도했고 결론:
- **"담당(ball-in-court)"** 축이 유효: 지금 누가 움직여야 하는가(한백/시공사/운영사/현장).
- 플러그링크 5×5(단계×상태) 모델과 정합. 상태가 곧 누구 차례인지를 결정.
- **정체일**(마지막 진척 후 경과일)이 핵심 지표. 노션엔 없음(공정-정산 relation이 끊겨 계산 불가).
- 운영사 3사(플러그링크/SK일렉링크/현대엔지니어링)가 각자 시스템. 통합 관점이 이 앱의 부가가치.
- **주의**: 대시보드는 후순위. 단계 데이터가 먼저 쌓여야 의미. 접수→시공→정산 순으로 만든 뒤 얹는다.

## 6. 데이터 모델 = 추상화 계층의 인터페이스 스키마

아래는 **추상화 계층이 다루는 논리 스키마**다. 물리 저장은 지금 노션, 나중에 Postgres.
노션 구현에서는 각 엔티티가 노션 DB/속성에 매핑된다(§0-1). 필드명은 노션과 1:1 대응시켜 매핑을 단순화.

```
projects(id, mgmt_no, cpo, sales_org, gc_org, name, addr, bldg_type,
         contract_party, park_total, mgr, tel, mail,
         pre_install, pre_note, power_type, repl_type, biz_type,
         created_at, ...)
         └ 노션: 계약/현장관리 마스터 (collection://345f...)
contract_lines(id, project_id, term_years, qty, memo, pricing_rule_id,
               -- ★스냅샷: 단가 지정 시점의 값 복사(매트릭스 수정돼도 안 바뀜)
               snap_sales_unit, snap_cons_unit, snap_margin, snap_turnkey_unit,
               snap_t1_trigger, snap_t1_type, snap_t1_unit,
               snap_t2_trigger, snap_t2_type, snap_t2_unit,
               snap_t3_trigger, snap_t3_type, snap_t3_unit, priced_at, ...)
         └ 한 현장에 복수. 단가 지정 시 매트릭스 케이스 값을 여기 스냅샷
pricing_rules(id, active(bool), cpo, biz_type, power_type, term, repl_type, bldg_type, biz_year, start_date,
              sales_unit, cons_unit, margin, turnkey_unit,          -- 단가
              t1_trigger, t1_type, t1_unit, t2_trigger, t2_type, t2_unit,  -- 기성 트리거·유형·대당
              t3_trigger, t3_type, t3_unit,
              supervision_cost_bearer, safety_fee_bearer, note, updated_at)  -- 부담주체·프로모션
         └ 노션: 단가 매트릭스 (collection://dec6...). ★관리자 화면에서 CRUD(§3-1)★.
           active=false로 soft delete. 케이스는 미래 계약용 기준표(과거 계약은 스냅샷으로 고정)
documents(id, project_id, kind, filename, storage_path, status, reject_reason, uploaded_by, ...)
         └ 노션: 현장 페이지 첨부. kind=종류(번호 아님). 자동분류 결과가 여기 들어감
process(project_id, [마일스톤 날짜들...], status, ...)
         └ 노션: 공정관리 마스터 (collection://328f...)
settlements(id, project_id, pricing_rule_id,  -- 정책은 별도 아님. 규칙=매트릭스가 트리거도 가짐
            gita_1_plan, gita_1_collected(bool), gita_1_date, ... (2,3차),
            sales_1_date, sales_2_date, cons_1_date, cons_2_date, safety_fee, ...)
         └ 노션: 정산관리 (collection://28ac...). 기성 금액은 매트릭스+공정에서 계산
audit_log(id, project_id, actor, action, field, old, new, at)
         └ 협력사 직접입력이므로 필수. 노션엔 없음 → 이건 처음부터 자체 저장 고려
```

**핵심 불변식**:
- 한 현장에 여러 contract_line. 단가는 라인별.
- **단가 지정 = 스냅샷**(§3-1). 매트릭스 케이스를 라인에 지정하면 그 시점 값을 복사. 매트릭스 수정 소급 안 됨.
- 매트릭스 케이스는 지우지 말고 active=false. 과거 라인이 참조 가능.
- 서류는 kind(종류)로 식별. 번호 아님. (INTAKE_SPEC §3)
- `*` 접두 노션 속성은 API 조회 불가 → 노션 구현에서 우회 필요(rename 또는 다른 접근). null ≠ 빈값("조회 불가").
- 환경부 마감일은 없음(승인일 공란). 임의 생성 금지.
- **audit_log는 노션에 없다.** 협력사 직접입력 추적이 필요하므로, 이건 병행기에도 자체 저장소에 남기는 걸 고려.

## 7. 구현 순서 (제안)

Phase 0. **저장소 파악 + 추상화 계층 설계**
   - 지금 API route가 노션에 뭘 쓰는지, 자동분류가 뭘 하는지 읽기 (§0-1)
   - §6 논리 스키마를 인터페이스로 정의, 노션 구현으로 채우기
   - 인증/역할 골격
Phase 1. **접수** (INTAKE_SPEC) — 폼 저장(노션) → 검수/반려 → 단가지정(스냅샷) → 정산행 생성.
   지금 접수 흐름을 확장(현장정보+서류를 접수 때 다 받기). 기존 자동분류·노션 연동 재사용.
Phase 1-b. **관리자 단가 매트릭스 관리**(§3-1) — 케이스 CRUD·복제·비활성·검증. 접수의 단가지정이 여기 의존.
   Phase 1과 함께 또는 직후(단가 지정이 되려면 매트릭스가 관리 가능해야 함).
Phase 2. **시공** — 마일스톤 입력 + 공정 서류 + 상태흐름 (노션 공정관리 마스터에 read/write)
Phase 3. **공정→정산 트리거** — 마일스톤 완료 시 기성 단계 자동 오픈 (§3). 노션 수식이 이미 하는 부분 활용
Phase 4. **정산** — 기성 회수/지급 체크, 회수율, 원가(한백)
Phase 5. **대시보드** — 담당 + 정체일 + 3사 통합 조망
Phase 6. **(웹앱 완성 후) 노션 → 자체 DB 이관** — 추상화 계층의 구현만 교체.
   `*` 속성 rename, 데이터 마이그레이션. **이 시점까지 노션 병행.**

각 Phase는 노션 병행 하에 진행. 컷오버는 모듈별로, 절대 dual-write 하지 않음(한 필드를 두 곳에 안 씀).
**노션을 벗어나는 건 맨 마지막(Phase 6)**, 웹앱이 충분히 완전해진 뒤. 그 전까지 노션이 정본.
